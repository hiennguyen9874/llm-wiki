audio.cpp is a high-performance C++ audio inference framework built on `ggml` that runs modern local audio models — TTS, voice cloning/conversion, ASR, diarization, VAD, separation, alignment, codecs, and music/media workflows — behind shared CLI and server entry points instead of per-model Python environments, reporting 100+ models and 170+ variants at v0.9.0 with CUDA TTS paths 1.8x–8x faster than their Python references (**Reported**).[^audio-cpp-repo]

## Framework identity and scope

- `audio.cpp` is a portable native stack targeting Windows, Linux, and macOS across NVIDIA, AMD, Apple Silicon, and CPU-only machines, motivated by avoiding per-model Conda environments and dependency conflicts (**Reported**).[^audio-cpp-repo]
- Stated goal is highly optimized reusable building blocks so new model integrations come up faster, shared components improve once for many families, and end-to-end paths stay efficient, maintainable, and portable (**Reported**).[^audio-cpp-repo]
- Source snapshot is release v0.9.0 dated 2026-09-30, described as 100 days / 100+ models / 170+ variants; growth history states v0.8.0 at 80+ families and 120+ variants, 0.7 at 62 families and 85+ variants, 0.6 at 49 families and 70+ variants, 0.5 at 44 families, and 0.1–0.4 building the first TTS/ASR/music/separation/VAD/diarization/codec/VC wave with VibeVoice 1.5B/7B, LoRA loading, early streaming, and CUDA Conv1DTransp speedups (**Reported**).[^audio-cpp-repo]
- v0.9.0 additions are Maya1, GigaAM v3 and Multilingual, SAM Audio, SAMSONE, Tone Color VC, HTDemucs six-stem separation, and MOSS-TTSD, plus a WebUI enhancement/denoising tab, speaker-tagged Nemotron ASR, ZipVoice streaming, and Higgs Audio / MOSS-TTS / Echo-TTS / ACE-Step / BS-RoFormer performance and memory work (**Reported**).[^audio-cpp-repo]
- Upstream is `0xShug0/audio.cpp` with GGUF weights at `audio-cpp/audio.cpp-gguf`, a ModelScope mirror, a Colab notebook, and an Audio Model Architecture Atlas over 100+ models; model weights keep their original licenses, tracked per family in `docs/model_licenses.md` with commercial-use notes (**Reported**, with unfetched-pointer limit).[^audio-cpp-repo]

## Runtime, backends, and builds

- Highlights claim parity tooling against Python references, performance-focused execution with reusable sessions and batch offline inference optimized for CUDA, and experimental JSON pipeline support (**Reported**).[^audio-cpp-repo]
- Backends are CUDA, HIP/ROCm, Vulkan, Metal, and CPU behind the shared entry points; the server-config note states CUDA is the optimized path while CPU/Vulkan/Metal/HIP serve portability and testing with possibly lower performance and coverage (**Reported**).[^audio-cpp-repo]
- Base requirements are GCC 13+ plus CMake and the wanted backend toolkit on Linux, VS Build Tools 2022 with MSVC x64/SDK/CMake/Ninja/OpenMP on Windows, and Xcode/CLT plus CMake with Metal via `xcrun` on macOS; helper scripts write aligned directories such as `build/linux-cuda-release` (**Reported**).[^audio-cpp-repo]
- Composite builds select `full` (default, for releases/Docker), `core` (runtime without optional families), or `custom` with `--model-set`/`--models` (e.g. `qwen3_tts,pocket_tts,qwen3_asr`), backed by `AUDIOCPP_MODEL_SET`/`AUDIOCPP_MODELS`; Linux/macOS flags include `--cuda-arch native`, `--ccache` (rebuilds about 14x faster), `--native-cpu OFF` for portable kernels, `--deployment-build` for compiled package specs, and `--native-model-manager`; Windows offers the same via `-Preset`/`-ModelSet`/`-Models`/`-DeploymentBuild`/`-NativeModelManager`; Metal, HIP/ROCm (mutually exclusive with CUDA), Nix/NixOS, and optional server frontend modules from the `external/audio.cpp-server-frontends` submodule (e.g. `audio_decode;mp3_encode`) are documented separately (**Reported**).[^audio-cpp-repo]

## Distribution and model management

- Release binaries cover Windows x64 (CPU, Vulkan, CUDA 12.4/13.3), Ubuntu x64 (CPU, Vulkan), and macOS arm64/x64 (Metal); Windows CUDA ships a separate `cudart` archive extracted beside the binaries, and community HIP/ROCm Windows packages with bundled ROCm runtime follow upstream versions in ROCm 6.4 and 7.1 tracks; macOS also has a Homebrew tap (`0xShug0/audio-cpp`) and Docker offers CUDA/CPU images for CLI and server use (**Reported**).[^audio-cpp-repo]
- Normal downloads use `tools/model_manager_v2.py` over `model_specs/*.json` preferring ready GGUF; native builds with `-DAUDIOCPP_BUILD_NATIVE_MODEL_MANAGER=ON` provide `audiocpp_model_manager` (`list`, `info`, `install`, `clean`, `remove`) with bundled TLS and no libcurl; the legacy safetensors catalog is renamed to `tools/model_manager_deprecated.py`; released packages live at `audio-cpp/audio.cpp-gguf` with a community mirror at `mirek190/audio.cpp` (**Reported**).[^audio-cpp-repo]
- All released families support GGUF loading per the v0.9.0 note; full package/quantization detail is delegated to the [audio.cpp GGUF Model Packages](audio-cpp-gguf-packages.md) concept and the external GGUF guide and Q8 report, which were not fetched (**Reported**, with unfetched-pointer limit).[^audio-cpp-repo]

## Interfaces: CLI, server, WebUI, pipelines

- CLI shape is `audiocpp_cli --task <task> --model <path> [--family <family>] [--backend <backend>] [--mode <mode>]`, with tasks `vad|asr|diar|sep|gen|tts|clon|vc|s2s|align|vdes|spk|svc`, optional `--family` disambiguation, backends `cpu|cuda|vulkan|metal|best`, and `offline|streaming` modes where the model supports streaming; quick starts cover [Pocket TTS](pocket-tts.md) TTS/cloning (including a Spanish `--load-option language=spanish --voice-id alba` example), [Qwen3-ASR family](qwen3-asr-family.md) ASR, and SeedVC conversion (**Reported**).[^audio-cpp-repo]
- Interface options include `--load-option`/`--session-option`/`--request-option` key/value knobs, `--config`/`--weight` asset selection, `--device`/`--threads`, `--help`/`--inspect`/`--list-loaders` discovery, `--batch-text-file`/`--batch-text-dir`/`--batch-audio-dir`, `--audio-chunk-mode auto|fixed|vad|none`, `--request-sequence` with `--metrics` (wall time, duration, RTF, speed, rate, channels), `--segments-out`/`--turns-out`/`--words-out`, and VAD chunk windows with max/merge-gap/padding tuning (**Reported**).[^audio-cpp-repo]
- `audiocpp_server` takes a JSON config (example registers `pocket-tts` and `qwen3-asr` with load/session options), supports `lazy_load` with per-model override plus `max_loaded_models` LRU eviction where `0` keeps everything and `1` enforces a single resident model, and exposes `GET /health`, `GET /v1/models`, `POST /v1/audio/speech`, `POST /v1/audio/transcriptions[/details]`, `POST /v1/audio/alignments`, and `POST /v1/tasks/run|batch`; the source warns lazy loading never unloads after first use except via the cap (**Reported**, with unfetched `app/server/README.md` limit).[^audio-cpp-repo]
- The embedded SvelteKit/TypeScript WebUI compiles into the server so no Python or separate frontend files are needed; `--ui --ui-management --backend cuda` at `http://127.0.0.1:8080` enables catalog browsing, downloads, uploads, and model switching, while `--ui` with a config alone is locked down; Docker UI downloads need a writable `/app/models`; features include background preparation, long-text split-and-merge, a browser-local voice library, microphone recording, and near-live ASR input, with some preparation jobs still invoking the Python model manager (**Reported**).[^audio-cpp-repo]
- The Arena tab compares TTS, voice conversion, and ASR side by side on one shared input with queued models/variants, metrics, and sorting; pipelines are experimental JSON workflows (`--pipeline`, `--list-pipelines`, `--workflow-input key=value`, `--out-dir`, declared `final_audio`) with a same-language speech-redub example chaining Qwen3 ASR chunked transcription and Qwen3 TTS re-synthesis over a 418-second / 8,091-character test asset (**Reported**).[^audio-cpp-repo]
- Tests combine `tests/warmbench.py` long-lived multi-request, parity-against-Python, and session-reuse harnesses with model-specific entry points, plus `tools/audiocpp_cli/run_audiocpp_cli_path_tests.py` for offline/streaming CLI paths; Python-reference setup is described as more time-consuming than the C++ side because each model brings its own reference stack (**Reported**).[^audio-cpp-repo]

## Performance and quantization (Reported, same-setup claims)

- Headline v0.9.0 figures state multiple TTS paths run 1.8x to up to 8x faster than Python references while cutting end-to-end latency 45%–85%; the older Performance Metrics section instead states 1.8x to up to 10x and 45%–90% but is explicitly flagged as the initial-release baseline that later paths have substantially improved, so the v0.9.0 headline is the fresher number and both share the RTX 5090 / Ubuntu / CUDA / framework-API-call (not CLI) measurement scope (**Reported**).[^audio-cpp-repo]
- Standout end-to-end figures include [VibeVoice-1.5B](vibevoice-1.5b.md) generating a 93.9-minute podcast in 18.2 minutes at 10 diffusion steps without quantization (about 5.15x real time), Supertonic 3 generating about 10 hours in 3 minutes on RTX 5090 (up to 200x+ real time CUDA, 6x+ CPU, 47 ms TTFT streaming), Q8 packages up to 1.53x faster with up to about 37% less peak VRAM on Higgs Audio / Fish Audio / Voxtral routes, TranscrIA messy-French-meeting ASR matching WER at about 1/4 wall time on Nemotron 3.5 ASR, and tested VoxCPM2 runs up to 2.56x faster on Apple Silicon Metal (**Reported**).[^audio-cpp-repo]
- One-shot Python-relative wins list VeVo2 5.03x, Pocket TTS 3.68x, MioTTS 2.73x, MOSS-TTS-Local 2.33x, Qwen3 TTS 1.83x, and VibeVoice 1.40x; long-lived-session wins list Pocket TTS 3.22x, Qwen3 TTS 2.74x, MOSS-TTS-Local 2.66x, MioTTS 2.28x, VibeVoice 1.77x, and VeVo2 1.75x; long-form RTF standouts include Pocket TTS about 48x, OmniVoice about 20x, and Supertonic about 188x on CUDA (about 6.2x on CPU); bars below 1.0x mark paths still needing optimization (**Reported**).[^audio-cpp-repo]
- Quantization is exposed per session via `--session-option <family>.weight_type=<mode>` plus family-specific knobs, alongside standalone GGUF packages, but the source treats it as route-specific rather than a safe default: ACE-Step 1.5 low-precision runs could fail with `planner masked decode found no valid token`, VeVo2 non-`fp32` outputs showed weaker `fp32` similarity and possible length shifts, `q8_0` gained only about 3.8% on Qwen3-TTS and 3.6% on VeVo2 in the checked routes, while Qwen3-TTS `q8_0` cut peak VRAM about 25.0% and peak RAM about 3.7% (**Reported**).[^audio-cpp-repo]
- Memory-saver session options (default output unchanged, reduced workspace or released staged state rebuilt on later requests) exist for ACE-Step, DramaBox, HeartMuLa, Stable Audio, OmniVoice, VoxCPM2, and Echo-TTS; GGUF is a container, not a universal adapter, so llama.cpp/whisper.cpp GGUF files are not automatically compatible, and `Build_xcframework.sh` is flagged outdated (**Reported**).[^audio-cpp-repo]

**RTF versus RTFx convention**

- A commenter notes that real-time factor is conventionally processing time divided by audio duration, where smaller is better: a 4 s clip generated in 1 s gives RTF 0.25. A third-party TTS benchmark author replies that its metric is the inverse (audio divided by processing time, higher is better) and agrees to relabel it RTFx (**Reported**).[^audiocpp-10-hours-thread]
- audio.cpp's own table reports both forms consistently: RTF 0.0319 beside 31.37x RT, since 1/0.0319 is about 31.4 (**Observed** by arithmetic on the captured table). Check which direction an "RTF" column uses before comparing TTS numbers across sources (**Synthesis**).[^audiocpp-10-hours-thread]

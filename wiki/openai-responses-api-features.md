The bare `openai:` prefix is not just the newest dialect but the one that carries every capability the vendor page describes as available "only on `OpenAIResponsesModel`": reasoning controls, computer use, server-side state that spares resending history, compaction that summarises it, a background mode that outlives a synchronous request, a half-price batch path, and a socket that keeps a tool loop off HTTP[^pydantic-openai-2026] These are transport and state features rather than model features, which is why they cluster: each one trades Pydantic AI's default of sending full history from the client for something OpenAI holds on the other side. Route selection, provider configuration and the Chat/Decisions dialects are in [OpenAI models in Pydantic AI](openai-models-in-pydantic-ai.md).

## Reasoning mode and reasoning context

The GPT-5.6 and GPT-6 families expose two reasoning modes: `standard`, the default, and `pro`, which does more model work for reliability on hard tasks at higher latency and token cost[^pydantic-openai-2026] Mode is independent of effort — any pair is valid, the unified `thinking` setting only ever influences effort, so `pro` is reached only by setting `openai_reasoning_mode` explicitly and there is no separate `pro` model to select[^pydantic-openai-2026] The setting is ignored on models whose profile does not set `openai_responses_supports_reasoning_mode`.

Reasoning *context* is the separate question of which prior turns' reasoning items the model may sample over: `auto` defers to the model's default, `current_turn` exposes only the active turn, and `all_turns` renders compatible earlier-turn items into the next sample, which requires access to earlier response items through `previous_response_id`, a conversation, or replayed history and behaves like `current_turn` on a first request[^pydantic-openai-2026] Pydantic AI sends `all_turns` by default on models that support it, so earlier reasoning stays available without opting in — consistent with how prior thinking is returned to other models — at the cost of extra input tokens on every follow-up sample; set `auto` or `current_turn` to stop that[^pydantic-openai-2026] `auto` and `current_turn` go to any reasoning model, while `all_turns` is sent only where the profile sets `openai_responses_supports_reasoning_context` (currently the GPT-5.4, GPT-5.5, GPT-5.6 and GPT-6 families) and is otherwise ignored[^pydantic-openai-2026]

## Native tools and computer use

Web search, code interpreter, image generation and file search are natively supported through the framework's native-tools feature; computer use is not, and is enabled instead by passing an `openai.types.responses.ComputerToolParam` in the `openai_native_tools` setting[^pydantic-openai-2026] The gap matters for anything that reads history or streams: computer use does not produce `NativeToolCallPart` or `NativeToolReturnPart` parts and emits no streamed events, so a UI cannot render it the way it renders the other four[^pydantic-openai-2026]

## Server-side response state

`openai_previous_response_id` lets a request reference an earlier response so OpenAI reconstructs the conversation — reasoning items included — from server-side state, and `'auto'` selects the most recent `provider_response_id` in the history and omits every message before it; the same chaining applies inside a run across tool-call continuations and retries, so OpenAI never sees duplicate copies of a message[^pydantic-openai-2026]

The safety mechanism is a digest. Each response created with the setting, or with `openai_transport='websocket'`, records a digest of its parts and of the history it was created from as `ModelResponse.history_digest`; if the response or those messages changed since — a history processor, compaction, or your own redaction and trimming — the request sends the full history instead, so the model sees the change rather than the server's stale copy, and a response without a digest is treated the same way, costing no extra tokens because it simply resends[^pydantic-openai-2026] Two operational rules follow: every model continuing the same conversation needs the same `history_digest_key`, including workers under [durable execution](pydantic-ai-durable-execution.md), and computing the digest serialises history on every request, which is local work proportional to conversation length[^pydantic-openai-2026]

Pass the whole conversation with `all_messages()`, even though only the messages after the latest response are sent: a history missing its earlier messages, such as `new_messages()` from a later turn, looks exactly like one that compaction or a processor trimmed, so it counts as changed and is sent as-is without `previous_response_id` — the model does not see what was left out and nothing raises[^pydantic-openai-2026] A concrete `provider_response_id` may seed a run instead of a history, and the chain then extends automatically across the run's tool-call continuations and retries[^pydantic-openai-2026]

Two things end a chain. An encrypted `CompactionPart` produced by another compatible provider such as the Codex backend, or by an endpoint that does not share server state, ends it even with a concrete seed, and the next request sends the compaction item and later messages instead; inline compactions from an endpoint that shares server state remain chainable[^pydantic-openai-2026] And a response from a model before GPT-5.6 whose request named a revealed tool in `tool_choice` should not be continued, because that request declares the tool in `tools` rather than its `additional_tools` item, leaving the tool out of the stored input[^pydantic-openai-2026]

### Durable conversations

OpenAI's Conversations API is the other server-side option, reached with `openai_conversation_id`; the ID a response belongs to is stored in `provider_details['conversation_id']`, and `'auto'` reuses the most recent same-provider conversation ID from the history and sends only the new input items after that response[^pydantic-openai-2026] The asymmetry with `previous_response_id` is the point: OpenAI owns the conversation, so client-side edits before that response — from a history processor or from compaction's Pydantic-side summary — never reach the model, and where `previous_response_id` falls back to resending the full history, a conversation has nothing to fall back to without duplicating its items[^pydantic-openai-2026] `auto` only reuses a conversation from the current Pydantic AI conversation when message-level `conversation_id` values exist, and Pydantic AI never creates the OpenAI conversation for you — create it with the OpenAI client and pass the ID[^pydantic-openai-2026] The two settings are mutually exclusive, because OpenAI's `conversation` and `previous_response_id` parameters are[^pydantic-openai-2026]

## Compaction

`OpenAICompaction` is the capability form of OpenAI's history compaction, which replaces older messages with an encrypted summary; with no arguments it runs in **stateful** mode, configuring OpenAI's server-side auto-compaction through `context_management` on the ordinary `/responses` request and letting OpenAI trigger at a threshold it manages[^pydantic-openai-2026] Stateful mode is compatible with `openai_previous_response_id='auto'` and `openai_conversation_id`, and after a compaction later requests send only the compacted window from the latest compaction item onward — necessary because the Responses API processes and bills replayed items that precede a compaction item, so resending them would regrow the context[^pydantic-openai-2026] A compaction item from the Codex backend or the [Pydantic AI Gateway](pydantic-ai-gateway.md) is reusable because those share OpenAI's encryption keys; one from Azure OpenAI is not, having its own[^pydantic-openai-2026] `token_threshold` overrides the trigger.

**Stateless** mode (`stateless=True`) calls the `/responses/compact` endpoint through a `before_model_request` hook instead, for zero-data-retention environments, `openai_store=False`, explicit out-of-band control over when compaction runs, or when the per-request cost of stateful mode matters: stateful mode sends `context_management` on every `/responses` request, not only near the threshold, which the vendor measured at roughly 50 ms of added server processing per request and which setting `token_threshold` did not reduce[^pydantic-openai-2026] Stateless mode requires either `message_count_threshold` or a custom `trigger` callable; the mode is inferred from which parameters you pass, `stateless=True`/`False` states it explicitly, and mixing parameters from both modes raises a `UserError`[^pydantic-openai-2026] For lower-level control, `OpenAIResponsesModel.compact_messages` is callable directly.

## Text phases

Models that support it label each assistant message with a `phase`: `commentary` for the preamble written while working, `final_answer` for the answer, surfaced as `'phase'` in `TextPart.provider_details` and sent back on the next request only where the profile sets `openai_supports_phase`[^pydantic-openai-2026] While streaming, the phase is set on the `PartStartEvent` that opens each text part including its first chunk, so commentary and the final answer can be routed differently as they generate — but prefer `run_stream_events` for this, because `run_stream` treats the first text part as the final output, which on a model that emits a preamble is usually `commentary`[^pydantic-openai-2026]

## Background mode

`openai_background=True` moves a long request server-side — large reasoning jobs or tool-heavy runs that would exceed the practical duration of a synchronous request — and Pydantic AI continues a response that comes back `'queued'` or `'in_progress'` to completion transparently, for both `agent.run` and `agent.run_stream`, stitching the result into one `ModelResponse` with live token activity surfaced as it arrives[^pydantic-openai-2026] The cost is time to first token, since the request queues, and a fixed polling interval while pending. To end the run rather than wait, add `PendingModelResponse` to `output_type`: the run ends as soon as the response is queued, and re-running the agent with that run's history checks on the same background response[^pydantic-openai-2026]

## Batch API

`OpenAIResponsesModel` reaches OpenAI's Batch API at 50% of the standard price: one model per batch, up to 50,000 requests in an input file of up to 200 MB[^pydantic-openai-2026] File ownership is the operational detail — the process that submitted a batch deletes the input file when it collects the results, while a batch collected elsewhere, such as from a stored `PendingModelResponse` history, leaves the file for OpenAI to delete after 30 days, because only the uploader knows deletion is safe[^pydantic-openai-2026] Batched responses are stored unless `openai_store=False`, so they can be continued with `openai_previous_response_id`.

The Batch API is OpenAI's own, and the boundary is drawn by a profile flag: `OpenAIChatModel`, Azure OpenAI, and providers with their own class that implement Responses such as OpenRouter do not use it by default, and it is not available through the [Pydantic AI Gateway](pydantic-ai-gateway.md) yet — the gateway path needs `OpenAIProvider` with an OpenAI key[^pydantic-openai-2026] `OpenAIProvider` sets `openai_supports_batch_api`, including when given a compatible endpoint's `base_url`; a server that does serve `/v1/files` and `/v1/batches` for `/v1/responses` needs the flag set in the model's profile, and an endpoint without them needs it set to `False`[^pydantic-openai-2026] Batch cannot combine with background mode — that raises a `UserError` when the request is made — and per-request `timeout` and `extra_headers` are unsupported, so they belong on the client; a streamed run receives the batch result's events all at once[^pydantic-openai-2026] The mechanism around all of this — the `BatchModelRequests` capability, batch assembly, splitting, resubmission and the `PendingModelResponse` cycle — is in [batch processing](pydantic-ai-batch-processing.md), and OpenAI's `PendingModelResponse` continuation shares that cycle with its background mode.

## Responses WebSockets

A run that makes many requests, such as one with a tool loop, can send them over a single socket instead of a new HTTP request each time: install `pydantic-ai-slim[openai-realtime]`, then set `openai_transport='websocket'` on the model, the agent or a run, knowing that other models ignore the setting so configuration-supplied model strings keep working[^pydantic-openai-2026] Each run opens a socket on its first eligible request and closes it when the run ends; entering the agent or the model keeps one socket for back-to-back runs or an app's lifetime, and it closes when the last run or context using it ends[^pydantic-openai-2026]

WebSocket mode defaults `openai_previous_response_id` to `'auto'`, including over HTTP overflow, unless you set that or `openai_conversation_id`[^pydantic-openai-2026] That is where the saving comes from: in a tool loop each tool result goes out on the open socket without the conversation before it, while a single-request run pays for the handshake and gains nothing[^pydantic-openai-2026]

Ownership is by instance and event loop. The socket belongs to the `OpenAIResponsesModel` instance on one loop, and runs on that instance share it — concurrent runs, a run in another agent handed the same instance, and a nested run a tool starts on the parent's `ctx.model`; another loop gets its own socket, capacity limit and cleanup, and agents built separately from the same model string have separate instances[^pydantic-openai-2026] Within a socket, concurrent requests occupy separate `stream_id` lanes: a request continues on the lane holding its previous response, one without earlier messages starts a new conversation on a free lane, OpenAI runs up to 16 responses at once and accepts 32 named lanes, and past 32 a request reuses the least recently used free lane whose cached conversation then replays its history[^pydantic-openai-2026] Lanes are opt-in per host: they run only when the SDK client's WebSocket host is `api.openai.com`, and on any other host — xAI, Azure's `/openai/v1` through `OpenAIProvider`, a proxy in front of OpenAI — the socket runs one request at a time and sends the rest over HTTP, fixed by `profile=OpenAIModelProfile(openai_responses_supports_websocket_stream_id=True)` or disabled on OpenAI's own host with `False`[^pydantic-openai-2026]

Failure granularity is the useful part: a provider error, a failed or incomplete response, or a stream closed early ends only that request and leaves the socket open, while a transport failure during a request closes the socket and raises `ModelConnectionError` so a `ModelFallback` can take over — and Pydantic AI does not resend after a disconnect, since the provider may have acted on the request[^pydantic-openai-2026] OpenAI closes a socket after 60 minutes; ten minutes before that, new requests open a new one and the old closes once its responses finish, and a server close while idle means the request was never sent, so it moves to a new socket once before falling back to HTTP[^pydantic-openai-2026]

In WebSocket mode the following requests use HTTP instead, and only some warn with `UnsupportedSettingWarning`:

| Condition | Warns |
| --- | --- |
| No run, `async with agent:` or `async with model:` keeps a socket open, as with a direct `model.request()` | No |
| A [durable execution](pydantic-ai-durable-execution.md) activity, step or task has no explicit model or agent context outliving the unit on its loop | No |
| The request uses background mode or resumes a suspended response | No |
| No lane is free, or 16 responses are already running | No |
| `extra_headers` or the SDK client's default headers differ from the handshake headers | No |
| The SDK client authenticates per request — API key callback, workload identity, Azure AD token provider or HTTP client auth — including auth added after the socket opened | Yes |
| The profile sets `openai_responses_supports_websocket` to `False` | Yes |
| The OpenAI SDK cannot configure authentication for its socket client, as with Bedrock Mantle | Yes |
| The WebSocket extra is missing, or the async backend is not asyncio, such as Trio | Yes |
| A transport failure prevents the connection from opening — TLS, proxy, DNS, connect timeout — before any `response.create` | Yes |

An HTTP-level handshake rejection stays an error; after a failed connection, later requests in the same run or outer model/agent context use HTTP without retrying the handshake or warning again, and the next run or context tries a socket again[^pydantic-openai-2026] The `openai_responses_supports_websocket` flag defaults to `False` for `AzureProvider` or an `AsyncAzureOpenAI` client, the Pydantic AI Gateway, the `openai-chatgpt` and `openai-codex` OAuth providers, and `OpenAICodexModel`, because their credentials or session headers are added to HTTP requests only; Azure or the gateway with static credentials can opt in through the profile, while the OAuth providers and `OpenAICodexModel` always stay on HTTP[^pydantic-openai-2026]

Socket limits follow from the socket living outside the SDK client's HTTP stack. The `websockets` library opens it, so the client's proxy and CA bundle don't apply — the socket takes its proxy from the environment such as `HTTPS_PROXY` and Python's default TLS settings — and `websocket_connection_options` passes options such as `compression` or `write_limit`, with `max_size` and `max_queue` defaulting to `None` so a large event such as an image result is not capped[^pydantic-openai-2026] Compaction and token counting still use HTTP; a socket request rejected with 408, 409, 429 or 5xx before its first event retries up to the SDK client's `max_retries` or `ModelSettings['max_retries']`, respecting `Retry-After` and `retry-after-ms` and otherwise backing off exponentially with jitter, propagating any wait longer than 60 seconds to the caller and set `max_retries=0` when a durable engine owns retries; disconnects after response events start propagate[^pydantic-openai-2026]

With instrumentation on, each request's `chat` span records `pydantic_ai.transport` as `'websocket'` or `'http'`, or under Temporal on the model activity span within that trace, and HTTP-only mode leaves the attribute unset[^pydantic-openai-2026] The mechanism is separate from OpenAI's Realtime sessions for audio and live interaction, which are compiled in [realtime voice agents](pydantic-ai-realtime-voice.md).
